## S1: build on macOS with Apple Silicon

**Question.** Does the merged OpenPLC Editor v4.3.5 build and package on
this host?

**What we did.** `npm run build`, then
`electron-builder build --mac dir --arm64` with
`CSC_IDENTITY_AUTO_DISCOVERY=false`, so the build has no certificate.

**Result.**

| Measure | Value |
|---------|-------|
| `npm run build` | Pass, 126 s |
| Package, arm64 `.app` | Pass, 129 s. The download of Electron 35.0.0 took 116 s of this. |
| Start of the packaged app | Fails. macOS stops the process with signal 9. |

The `afterPack` script `scripts/mac-inject-local-network-usage.js` writes a
new `LC_UUID` into the main binary. This change makes the ad hoc signature
of Electron incorrect. `codesign -v` reports "invalid signature". On Apple
Silicon, macOS does not start a binary with an incorrect signature. Upstream
does not see this fault, because its release build signs the app after this
step. After `codesign --force --deep -s -`, the app starts and
`--cli --version` returns `4.3.5`.

**Decision.** P1 adds an ad hoc signature after `afterPack` when the build
has no certificate. Each unsigned macOS build needs it.

## S2: run a sample project in the simulator

**Question.** Does an LD program compile and run in the built-in simulator?

**What we did.** The packaged CLI created an LD project with an isolated
`--user-data` folder. The program has one rung: the contact `Motor` drives
the coil `Lamp`. The CLI compiled it for the target `OpenPLC Simulator`.
The CLI cannot open the simulator with no window: `debug open` reports
`target_unknown`. Thus the script
[`spikes/simulator/run.ts`](../../spikes/simulator/run.ts) boots the
firmware with the editor's own `SimulatorModule`, `VirtualSerialPort`, and
`ModbusRtuClient`. It forces `Motor` and reads `Lamp`. The sample project is
in [`spikes/simulator/sim-ld/`](../../spikes/simulator/sim-ld/).

**Result.**

| Measure | Value |
|---------|-------|
| First compile | Fails: "Platform 'arduino:avr' not found" |
| Download of the `arduino:avr` core | 387 MB in the editor state folder |
| Compile after the download | Pass, 12 s |
| Boot and first debug reply | 2.6 s |
| Force `Motor` TRUE, then FALSE | `Lamp` follows each time |
| Scans in 1 s of wall time | 51. The task interval is 20 ms, so the target is 50. |
| Upstream test `debug-e2e.test.ts` with this firmware | 6 of 6 pass |

Findings:

- The app does not ship the `arduino:avr` core. The editor installs it with
  the first board package, and this needs the network. The exit test of P1
  says "with no network", so P1 must ship the core or a copy of it in the
  installer.
- The CLI cannot drive the simulator. A test of the simulator in CI needs a
  script like the spike, or a change to the CLI.

**Decision.** The AVR simulator works for the P1 exit test, if the
installer holds the core.

## S3: the WebAssembly path

**Question.** Can the STruC++ output run as WebAssembly, with no AVR
emulator?

**What we did.** The script [`spikes/wasm/run.mjs`](../../spikes/wasm/run.mjs)
takes the STruC++ output of the S2 project. It compiles the configuration,
the POU, and a small host
([`spikes/wasm/host.cpp`](../../spikes/wasm/host.cpp)) with
`@yowasp/clang`, which is clang in WebAssembly. Upstream already ships this
package. Node loads the module with WASI preview 1. The host exports one
scan, a setter for `Motor`, and a getter for `Lamp`.

**Result.**

| Measure | Value |
|---------|-------|
| Compile and link, first run | Pass, 6.9 s to 7.8 s. Clang loads from `node_modules`. |
| Module size | 28.5 KB |
| Network | None |
| `Motor` TRUE, then FALSE | `Lamp` follows after one scan each time |

Findings:

- Upstream does not use this path for the simulator. Its tests of
  `wasm-toolchain` use a fake runner, so this spike is the first real
  compile of STruC++ output with it.
- The spike host knows the names of the variables. P5 needs a generic host
  that reads and writes variables through the debug table of STruC++
  (`debug-map.json` and `generated_debug.cpp`).
- The spike does not measure the scan rate. Clang can fold a loop of
  `LAMP := MOTOR`, so a count of scans with this program proves nothing.
  Measure it with a real program in P5.

**Decision.** The WebAssembly path works. P6 builds the plant simulation on
it. IronPLC stays a fallback that we do not need now.

## S5: the upstream build workflow for Windows and Linux

**Question.** Does the upstream workflow build Windows and Linux files in
this repository?

**Status.** Not run. `origin/main` on GitHub does not hold the merge of
v4.3.5 yet, so the workflow has no code to build. The test is: push `main`,
then start `release.yml` by hand with `platforms` set to `windows`, then
`linux`. The macOS job of `release.yml` needs the Apple secrets of upstream,
so it stays off until P1 changes it.

## S4: read all QElectroTech elements

**Question.** Can a TypeScript reader load each `.elmt` file of the
QElectroTech collection, and draw it as SVG?

**What we did.** A reader of about 300 lines with `fast-xml-parser`, the XML
parser that upstream already uses. It reads the definition, the names, the
primitives, and the terminals into a symbol model, and draws the model as
SVG. The source is in [`spikes/qet-elmt/`](../../spikes/qet-elmt/). It ran
on the shallow clone of `qelectrotech-elements` of 2026-11-21.

**Result.**

| Measure | Value |
|---------|-------|
| Element files | 9028 |
| Loaded with no error | 9028 |
| Time for all files (read, parse, draw) | 2.9 s, 0.32 ms for each file |
| Total SVG output | 44.4 MB |
| Tags that the reader does not know | none |
| Elements with no terminal | 2770 |
| Elements with at least one terminal with no name | 5127 |

The tags in the collection, by count: `line` 144834, `text` 84559,
`polygon` 54385, `rect` 49272, `terminal` 45185, `ellipse` 41426,
`dynamic_text` 27102, `arc` 13879, `circle` 4643, `input` 4. Format
versions: 0.100.0 (5568 files), 0.80 (1837), 0.90 (1330), 0.100.1 (205),
0.100 (70).

A visual check of 96 elements, a sample across the collection and a sample
from the PLC folders, shows correct lines, arcs, fills, colours, and text.

Findings:

- Some `dynamic_text` items overlap other text. QElectroTech places these
  texts with the metrics of Qt fonts. P2 must measure the text box, not only
  the anchor point.
- Hatch fills (`hor`, `ver`, `bdiag`, `fdiag`) draw as no fill in the spike.
  P2 adds SVG patterns for them.
- Many terminals have no name, so a terminal has no identity except its
  UUID. The data model already uses the UUID.
- The PLC folders hold almost only parts of vendor catalogues, which are out
  of scope. IOloom needs its own generic PLC I/O card symbols, with the
  channel data on each terminal. This work goes into P2.

**Decision.** The reader approach works. P2 builds on it.
